# Ⅲ.4.4 [과제3] AI 플랫폼 확대방안 설계

> **메타** | 요구사항: `PD-III-4b, SC3-01~SC3-07, OBJ-10` (9건) | Phase: Phase2 | 예상 분량: 7장

---

## 1. 거버닝 메시지

> **플랫폼 진단은 문서를 보고 판정하는 것이 아니라 AI 과제를 실제로 얹어보고 어디서 막히는지 측정하는 것이므로, 대상 과제 2건 이상을 현행 환경에 배치해 5개 축으로 계측한 뒤, 그 병목을 해소하는 5계층 목표 아키텍처를 설계하고 과제1의 위험등급과 과제2의 게이트가 시스템에서 자동 집행되도록 가드레일을 배치한다.**

- **서브메시지 1** — 진단의 판정 기준은 의견이 아니라 **측정값**이다. 처리량·지연·격리·권한·모델 교체 용이성 5개 축을 실측하고, 대고객 확대·신기술 수용·정책변화 수용 3개 관점에서 병목을 판정한다.
- **서브메시지 2** — 목표 아키텍처의 각 계층은 **"유연성을 어디서 확보하는가"** 에 답해야 한다. 모델이 바뀌어도, 서비스가 늘어도, 정책이 바뀌어도 **재구축 없이 흡수하는 지점**을 계층마다 지정한다.
- **서브메시지 3** — **계측 단위는 과제4의 정산 근거**가 된다. 못 세는 것으로는 정산하지 못하므로, 통합관리의 사용량·비용 계측 차원을 과제4의 정산 변수와 **동일한 값으로 고정**한다.

## 2. 본문

### 4.4.1 현행 플랫폼 배치 진단 및 개선과제 도출

**담당 요구사항 : SC3-01, SC3-02**

#### (1) 배치 진단 방식 — 실제로 얹어본다

**대상 과제 선정 기준**

| 기준 | 내용 |
|---|---|
| 유형 다양성 | **생성형 1건 이상 + 판별형 1건 이상**을 포함한다. 두 유형은 병목 지점이 다르다(생성형은 지연·토큰 처리량, 판별형은 배치 처리·재학습) |
| 도입 방식 | **자체개발 1건 + 외부 이용 1건**을 포함한다. 외부 이용은 연계 구간 병목이 별도로 드러난다 |
| 대고객 여부 | 대고객 확대 수용성을 진단하려면 **대고객 전환을 가정한 부하 시나리오**가 필요하므로, 내부 서비스라도 대고객 트래픽 배수를 적용해 측정한다 |
| **선정 결과** | **최소 2건, 권장 3건** — 10월 3개 과제 중 2건 + Agent 시나리오 1건 |

**배치 시나리오 3종**

| 시나리오 | 내용 | 목적 |
|---|---|---|
| **S-A 현행 부하** | 현재 예상 사용량 그대로 배치 | 기준선(baseline) 확보 |
| **S-B 대고객 확대** | 사용자 수를 **대고객 전환 가정치로 확대**(내부 사용자 대비 배수 적용) | 대고객 확대 수용성 판정 |
| **S-C 다중 모델·Agent** | 모델 2개 이상을 동시 서빙하고, **Agent가 다단계 호출**하는 흐름을 주입 | 신기술 수용성 판정 |

#### (2) 측정 항목 5개 축

| 축 | 측정 지표 | 측정 방법 | 판정 기준 |
|---|---|---|---|
| **① 처리량** | 초당 요청 수(RPS), 시간당 처리 건수, 토큰 처리량 | 부하 주입 후 단계적 증가, 오류율 급증 지점 확인 | S-B 시나리오 목표 부하를 **오류율 1% 이내로 처리**하는가 |
| **② 지연** | 평균 응답시간, P95·P99 지연 | 동일 부하에서 백분위 측정 | 대고객 서비스 허용 지연(착수 시 설정) 이내인가 |
| **③ 격리** | 서비스 간·기관 간 자원 간섭 정도 | 한 서비스에 부하를 몰아넣고 **다른 서비스의 지연 변화** 측정 | 타 서비스 지연 증가가 허용 범위 이내인가. **은행·상호금융 간 간섭이 발생하는가** |
| **④ 권한** | 접근통제 적용 지점, 권한 우회 가능 경로 | 권한 없는 계정으로 모델·데이터 접근 시도, 게이트웨이 우회 호출 시도 | **모델 엔드포인트 직접 접근이 차단되는가**(Ⅲ.2.6의 설계 전제 검증) |
| **⑤ 모델 교체 용이성** | 모델 교체에 소요되는 작업 단계 수와 시간, 애플리케이션 변경 필요 여부 | 서빙 중 모델을 다른 모델로 교체하는 작업을 실제 수행 | **애플리케이션 코드 변경 없이** 교체되는가. 교체 소요시간은? |

#### (3) 진단 축 3개 — 무엇을 판정하는가 (SC3-02)

| 진단 축 | 판정 질문 | 근거 측정 | 병목 유형 |
|---|---|---|---|
| **대고객 확대 수용성** | 내부 직원용에서 대고객으로 전환할 때 감당하는가 | S-B의 ①②③ | 처리량 한계 / 지연 초과 / 격리 실패 |
| **신기술 수용성** | 새 모델·새 서비스·Agent를 붙일 때 재구축이 필요한가 | S-C의 ⑤, ③ | 모델 결합도 / 오케스트레이션 부재 / 자원 격리 부재 |
| **정책변화 수용성** | 규제·내부 정책이 바뀔 때 **코드 수정 없이 반영**되는가 | ④ + 정책 변경 모의 적용 | 정책이 애플리케이션에 하드코딩됨 / 게이트웨이 부재 / 통제 적용 지점 산재 |

**정책변화 수용성 측정 방법** — 가상의 정책 변경 3건(① 특정 데이터 유형의 입력 차단 추가 ② 사용자별 호출 한도 하향 ③ 신규 필터링 규칙 추가)을 현행 환경에 적용해 보고, **적용에 필요한 작업 지점 수와 소요시간**을 측정한다. 애플리케이션마다 개별 수정이 필요하면 정책변화 수용성은 「미흡」으로 판정한다.

#### (4) 개선과제 도출 및 우선순위화

| 우선순위 기준 | 가중 | 판정 |
|---|---|---|
| **거버넌스 집행 가능성** | 최상 | 이 과제가 없으면 과제1·2의 통제가 시스템에서 집행되지 않는가 |
| **정산 가능성** | 상 | 이 과제가 없으면 과제4의 정산 변수를 계측하지 못하는가 |
| **대고객 개시 필수성** | 상 | 대고객 서비스 개시에 반드시 선행되어야 하는가 |
| 확장 대응 | 중 | 서비스 증가 시 병목이 되는가 |
| 운영 효율 | 하 | 운영 부담을 줄이는가 |

**개선과제는 이 기준으로 정렬하여 로드맵 3단계(4.4.5)에 배치**한다. 거버넌스 집행과 정산 가능성에 관련된 과제가 단기(6개월)에 배치되는 이유가 여기에 있다.

### 4.4.2 AI 플랫폼 목표 아키텍처 설계

**담당 요구사항 : SC3-03**

#### (1) 5계층 구조와 계층별 유연성 확보 지점

| 계층 | 구성요소 | **유연성을 어디서 확보하는가** |
|---|---|---|
| **L5 관측·운영 계층** | 통합 대시보드, 지표 수집, 로그·트레이스, 알림, 비용 리포트 | **수집 스키마의 확장성** — 새 지표·새 서비스가 추가되어도 스키마 변경 없이 태그로 흡수. 지표 정의를 코드가 아닌 **설정(configuration)** 으로 관리 |
| **L4 거버넌스·가드레일 계층** | 정책 엔진, 입출력 필터, 게이트 연동, 승인 검증, 등급별 통제 적용, 증적 적재 | **정책의 외부화** — 위험등급·필터 규칙·한도를 **정책 저장소에서 읽어 런타임 적용**. 규제·내규가 바뀌면 정책만 갱신하고 코드는 그대로 |
| **L3 오케스트레이션·Agent 계층** | 워크플로 엔진, Agent 런타임, 도구(tool) 레지스트리, 세션·상태 관리 | **도구·에이전트의 플러그인화** — 새 Agent나 도구를 **레지스트리 등록만으로** 추가. 워크플로를 선언형으로 정의 |
| **L2 모델·서빙 계층** | **모델 게이트웨이**, 모델 레지스트리, 서빙 런타임, 모델 라우팅, 캐싱 | **모델 추상화** — 애플리케이션은 게이트웨이의 **논리 모델명**을 호출하고, 실제 모델·공급자 매핑은 게이트웨이 설정에서 변경. 모델 교체 시 애플리케이션 무변경 |
| **L1 데이터 계층** | 데이터 레이크/웨어하우스, 피처 스토어, 벡터 스토어, 계보 저장소, 데이터 파이프라인 | **스키마 온 리드(schema-on-read)와 계보 표준** — 새 데이터 소스가 추가되어도 CP 기록 규격만 지키면 편입. 데이터셋 버전을 불변(immutable)으로 관리 |

#### (2) 계층 간 원칙

| 원칙 | 내용 |
|---|---|
| **단일 관문** | 모든 모델 호출은 **L2의 게이트웨이를 통과**한다. 네트워크 정책으로 모델 엔드포인트 직접 접근을 차단한다(Ⅲ.2.6의 권고 및 4.4.1 ④축 진단 결과 반영) |
| **정책과 실행의 분리** | L4의 정책은 데이터로 존재하고, 실행은 L2·L3에서 이루어진다. 정책 변경이 배포를 요구하지 않는다 |
| **증적의 동시 생성** | 모든 계층의 처리 결과는 **서비스 ID를 키로** 증적 저장소에 동시 적재된다. 사후 수집하지 않는다 |
| **테넌시 일관성** | 은행·상호금융 구분 태그가 L1~L5 **전 계층에서 동일한 값**으로 유지된다. 계층마다 다른 기준으로 나뉘면 정산이 성립하지 않는다 |

#### (3) 은행·상호금융 공동 존(Zone) 구조

| 영역 | 구성 | 비용 성격 |
|---|---|---|
| **공동 존 (Shared Zone)** | 게이트웨이, 정책 엔진, 모델 레지스트리, 관측 인프라, 공용 모델 서빙 자원 | **공통비** (항상 가동) |
| **전용 영역 (Dedicated)** | 기관별 전용 모델 인스턴스, 기관 전용 데이터 저장소 | **직접비** (귀속 명확) |
| **가변 자원 (Elastic)** | 사용량에 따라 확장·축소되는 서빙 자원, 토큰 소비 | **변동비** (사용량 비례) |

- **논리 분리 방식** — 계정·네임스페이스·태그 중 현행 클라우드 구성에 맞는 방식을 진단 후 확정하되, **분리 단위와 계측 태그를 반드시 일치**시킨다.
- 이 3분 구조가 **과제4의 공통비/변동비/직접비 구분과 1:1로 대응**한다. 아키텍처가 정산 구조를 결정한다.

### 4.4.3 AI 거버넌스 실행 프로세스의 시스템화 (가드레일)

**담당 요구사항 : SC3-04**

#### (1) 가드레일 목록 — 집행 시점별 배치

Ⅲ.2.6이 정의한 3개 집행 시점(배포 / 요청 / 응답)에 통제를 배치한다.

**① 배포 시점 (Deploy-time)**

| # | 가드레일 | 집행 방식 | 근거 |
|---|---|---|---|
| D1 | **위험평가 완료 검증** | 배포 요청 시 서비스 ID로 거버넌스 저장소를 조회, 위험평가서·등급이 없으면 파이프라인 중단 | 과제1 위험평가체계 / 거버넌스 점검항목 ⑥ |
| D2 | **등급별 승인 검증** | 등급에 따라 요구되는 결재를 확인. **고위험은 AI윤리위원회 의결번호가 입력되지 않으면 진행 차단** | 과제1 등급별 통제표 / AI RMF 3.4.2 |
| D3 | **승인 없는 모델 반입 차단** | 모델 레지스트리에 등록되지 않았거나 체크섬이 불일치하는 모델의 배포 차단 | 보안 안내서 제4장(자산·형상 관리) / 보안성 점검항목 ㉓ |
| D4 | **필수통제 이행 확인** | 등급별 필수통제 코드 목록과 실제 적용된 정책을 대조, 미적용 항목이 있으면 차단 | 과제1 등급별 통제표 |
| D5 | **형상·계보 등록** | 모델 버전, 학습 데이터셋 ID·해시, 기술문서 링크를 등록해야 배포 완료 처리 | CP3 / AI기본법 제34조제1항제2호 |
| D6 | **긴급정지 수단 확인** | 해당 서비스에 Kill switch가 연결되어 있는지 확인 | 보안성 점검항목 ㉕ / 보조수단성 ⑦ |

**② 요청 시점 (Request-time)**

| # | 가드레일 | 집행 방식 | 근거 |
|---|---|---|---|
| R1 | **권한 검증** | 호출자의 역할과 대상 서비스·데이터 등급을 대조(과제1 권한 매트릭스) | 보안성 점검항목 ㉔ |
| R2 | **입력 필터링** | 정상 범위 이탈 입력 사전 검토, 프롬프트 인젝션·탈옥 시도 탐지·차단 | 보안성 점검항목 ⑤⑥ |
| R3 | **중요정보 탐지·마스킹** | 목적 외 고유식별정보·개인(신용)정보 포함 여부 탐지 후 마스킹 또는 차단 | 보안성 점검항목 ⑦ |
| R4 | **호출 한도** | 사용자별·서비스별 질의 횟수 제한, 접근 빈도 모니터링 | 보안성 점검항목 ⑫ |
| R5 | **사용량 계측 기록** | 기관·부서/조합·서비스·모델·토큰·시간을 태그와 함께 기록 | 과제4 정산 근거 |

#### (2) 정책 엔진의 구조 — 정책은 코드가 아니라 데이터다

```
[정책 저장소]
  ├ 위험등급별 필수통제 정책      ← 과제1 등급별 통제표에서 생성
  ├ 입출력 필터 규칙 집합         ← AI 보안 준칙에서 생성
  ├ 사용자·역할별 호출 한도       ← 권한 매트릭스에서 생성
  ├ 데이터 등급별 마스킹 규칙     ← 데이터 거버넌스 정의서에서 생성
  └ 정책 버전 및 적용 이력
        ↓ 런타임 조회
[게이트웨이 / 파이프라인]  → 집행 → [증적 저장소]
```

**핵심 설계** — 정책 저장소의 내용은 **과제1의 산출물에서 기계적으로 생성**된다. 규정이 바뀌면 정책이 바뀌고, 정책이 바뀌면 집행이 바뀐다. 이 연결이 끊기면 *"규정과 시스템이 따로 노는"* 상태가 된다.

**정책 변경 절차** — 정책 변경은 **규정 개정 → 정책 갱신 → 적용**의 순서를 강제한다. 정책만 바꾸고 규정을 안 바꾸는 경로를 차단하기 위해, 정책 저장소의 각 정책에 **근거 조문 번호를 필수 속성**으로 둔다.

#### (3) 우회 경로 차단

| 경로 | 차단 방식 |
|---|---|
| 모델 엔드포인트 직접 호출 | 네트워크 정책으로 게이트웨이 외 접근 차단 |
| 파이프라인 외 수동 배포 | 운영 환경 배포 권한을 파이프라인 서비스 계정으로 한정 |
| 개발 환경에서의 운영 데이터 접근 | 환경 간 데이터 이동을 승인 절차로 제한 |
| 외부 SaaS AI 직접 이용 | 네트워크 차단 + 이용 신청 절차로 흡수. 차단이 불가한 구간은 **SDK 방식 의무 적용**(Ⅲ.2.6) |

#### (2) 계측 단위의 과제4 정합 — 이 절의 핵심 제약

**계측 차원은 과제4의 정산 변수와 동일한 값으로 고정한다.** 못 세는 것으로는 정산하지 못하기 때문이다(Ⅲ.3.4 사례 6).

| 계측 차원 | 값 | 과제4에서의 용도 |
|---|---|---|
| **기관** | 은행 / 중앙회(상호금융) | 1차 배분 기준 |
| **부서 / 조합** | 은행 : 본부 부서·영업점 / 상호금융 : **조합 → 조합지점** | 실비 정산의 배부 단위. **상호금융은 계측 키가 1단 더 깊다** |
| **서비스** | 서비스 ID | 서비스별 원가 귀속 |
| **모델** | 모델 ID·버전 | 모델별 단가 차이 반영 |
| **자원 유형** | 호출 / 토큰 / GPU 시간 / 스토리지 / 전용 인스턴스 | 변동비 산정 |
| **비용 성격** | 공통비 / 변동비 / 직접비 | 공동 존 3분 구조와 대응(4.4.2) |

**결측 대응** — 계측이 불가능한 구간이 발견되면 ① 계측 가능하도록 개선과제를 도출하거나 ② **대안 배부키**(인원수·거래 건수 등)를 지정한다. 대안 배부키를 쓰는 항목은 **과제4의 협의서 별표에 명시**한다.

**Agent 확장 대비** — Agent는 하나의 사용자 요청에 대해 **다단계·다중 모델 호출**을 수행한다. 호출 단위로만 계측하면 ① 비용이 사용자 요청과 무관하게 부풀고 ② 어느 업무가 얼마를 썼는지 귀속되지 않는다. 따라서 **세션(session)·작업(task) 단위 상위 키**를 계측 스키마에 처음부터 포함하고, 개별 호출은 그 하위로 묶는다.

#### (3) 라이프사이클 전 과정 데이터 파이프라인 (SC3-06)

과제1이 정의한 **CP1~CP6 체크포인트**와 과제2가 정의한 **L1~L10 단계**를 하나의 파이프라인으로 연결한다. **앞 단계의 산출물이 다음 단계의 입력으로 자동 이어지는 지점**을 명시한다.

| 연결 지점 | 앞 단계 산출 | 자동 전달 | 다음 단계 입력 |
|---|---|---|---|
| L1 → L2 | 적용대상 판정서 | 서비스 ID 발급 및 판정 결과 등록 | 타당성 검토의 판정 근거 |
| L3 → L4 | 데이터셋 등록(CP1·CP2) | 데이터셋 ID·버전·품질 지표 | 학습 실행의 입력 명세 |
| L4 → L5 | 모델 아티팩트, 학습 메타(CP3) | 모델 버전·해시·데이터셋 연결 | 검증 대상 지정 |
| L5 → L6 | 검증 결과, 위험평가 결과 | 등급·필수통제 코드 | 승인 요청서 자동 생성 |
| **L6 → L7** | **승인서(의결번호)** | **배포 게이트의 통과 조건으로 자동 전달** | 배포 파이프라인 진입 조건 |
| L7 → L8 | 배포 기록, 형상 정보 | 서비스 ID 기준 모니터링 대상 자동 등록 | 관측 계층의 수집 대상 |
| L8 → L9 | 모니터링 지표, 이상 이력 | 재평가 발동 조건 충족 시 알림 | 재평가 요청 |
| L9 → L6 | 재평가 결과, 등급 변동 | 등급 변동 시 **필수통제 정책 자동 갱신** | 승인 조건 재적용 |
| L10 | 폐기 결정 | 데이터·모델 삭제 대상 목록 생성, 증적 보존 대상 분리 | 폐기 실행 |

**"단절 없이"의 의미** — 각 연결 지점에서 **사람이 값을 다시 입력하지 않는다.** 재입력이 필요한 지점이 남아 있으면 그 지점이 곧 증적 누락과 오기(誤記)가 발생하는 곳이다. 진단(4.4.1)에서 재입력 지점을 세고, 개선과제로 도출한다.

| 제약조건 수용 | 구축사업이 이미 확정한 기술 결정을 제약으로 수용하고, 변경 필요 항목은 **「변경 요청 목록」** 으로 분리 제시 | 상시 |
| 합동 점검 | 격주 1회 요건 반영 여부 확인, 미반영 항목은 사유와 대안을 회의록에 기록 | 격주 |
| 미반영 처리 | 반영되지 않은 요건은 **「미반영 사유서」** 로 문서화하고 후속 이행 주체·시점을 명시 | Phase2 종료 시 |

## 3. 제안서용 요약 · 논리 구조

**논리 골격 : [실측 진단] → [목표 구조] → [자동 집행] → [계측 정합] → [단계 확장]**

- **[4.4.1 진단]** 문서 판정 ✗ / **실제 배치 후 측정** ○
  - 대상 : **생성형 1 + 판별형 1 + 자체개발 1 + 외부이용 1**, 최소 2건 권장 3건
  - 시나리오 3종 : **S-A 현행 부하 / S-B 대고객 확대 / S-C 다중 모델·Agent**
  - 측정 5축 : **처리량 · 지연(P95/P99) · 격리(타 서비스 간섭·기관 간 간섭) · 권한(게이트웨이 우회 시도) · 모델 교체 용이성**
  - 진단 축 3개 : 대고객 확대 / 신기술 / **정책변화 수용성 — 가상 정책 변경 3건을 적용해 작업 지점 수·소요시간 측정**
  - 우선순위 : **거버넌스 집행 가능성 > 정산 가능성 > 대고객 필수성 > 확장 > 효율**
- **[4.4.2 목표 아키텍처]** 5계층 × **"유연성을 어디서 확보하는가"**
  - L1 데이터 : *계보 표준 + 불변 버전* / L2 모델·서빙 : **모델 추상화(논리 모델명)** / L3 오케스트레이션 : *플러그인 레지스트리* / L4 가드레일 : **정책의 외부화** / L5 관측 : *스키마 확장성*
  - 계층 원칙 4개 : **단일 관문 / 정책과 실행 분리 / 증적 동시 생성 / 테넌시 일관성**
  - 공동 존 3분 : **공동 존(공통비) / 전용 영역(직접비) / 가변 자원(변동비)** — 과제4 비용 구조와 1:1 대응
- **[4.4.3 가드레일]** 집행 3시점 × 총 **17개 통제**
  - 배포 6개(D1 위험평가 검증 / D2 **고위험은 의결번호 없으면 차단** / D3 미등록 모델 반입 차단 / D4 필수통제 대조 / D5 형상·계보 등록 / D6 Kill switch 확인)
  - 요청 6개(R1 권한 / R2 입력 필터 / R3 정보 마스킹 / R4 한도 / **R5 사용량 계측** / R6 정책 버전 기록)
  - 응답 5개(P1 출력 필터 / P2 유해 차단 / **P3 생성 표시** / P4 이상 탐지 / P5 증적 적재)
  - **정책 저장소는 과제1 산출물에서 기계적으로 생성**, 각 정책에 **근거 조문 번호를 필수 속성**으로 → 규정과 시스템의 분리 차단
  - 우회 4경로 차단, 차단 불가 구간은 **SDK 의무 적용**
- **[4.4.4 통합관리·파이프라인]** 4축(품질·사용량·비용·성과) × [메트릭·집계 단위·주기·원천]
  - **계측 차원 6개를 과제4 정산 변수와 동일 고정** — *못 세는 것으로는 정산 불가*
  - **상호금융은 계측 키가 1단 더 깊다**(조합 → 조합지점)
  - 결측 시 개선과제 도출 또는 **대안 배부키 → 협의서 별표 명시**
  - **Agent는 세션·작업 단위 상위 키를 처음부터 스키마에 포함** ← 호출 단위만으로는 비용이 부풀고 귀속 불가
  - 파이프라인 9개 연결 지점, **"단절 없이" = 사람이 값을 재입력하지 않음** → 재입력 지점 수를 진단에서 계수
  - 화면 5종, **증적 조회 = 서비스 ID 입력 → 12개 항목 일괄**
- **[4.4.5 로드맵]** 3단계 × [목표 상태·과제·전제조건·**판단 게이트**]
  - **1단계(6개월) 집행 기반** — 게이트 : *게이트웨이 경유율 100% / 승인 검증 자동 차단 동작 / 월 사용량 정산 단위 집계*
  - **2단계(1년) 대고객·통합관리** — 게이트 : *대고객 부하 목표 충족 / **재입력 지점 0개** / 정책 변경이 배포 없이 반영*
  - **3단계(2년) Agent·확장** — 게이트 : *작업 단위 비용·증적 귀속 / 신규 모델 설정 변경만으로 편입 / 조합 단위 계측*
  - 투자 금액 미특정 — 구축 주체가 별도 사업이므로 **역량·범위 명세로 산정 지원**
  - 구축사업 연계 4조치 : **요건 3종 선전달 / 제약 수용 + 변경 요청 목록 분리 / 격주 합동 점검 / 미반영 사유서**

## 4. 시각적 표현 방안

### (a) 슬라이드 분할 구조 — 7장

| 장 | 내용 | 분할 패턴 |
|---|---|---|
| **1** | 진단 방식 — 배치 시나리오 × 측정 5축 | `상하 2분할` |
| **2** | 진단 축 3개 및 개선과제 우선순위 | `3분할 가로 열거` |
| **3** | 목표 아키텍처 5계층 | `중앙 다이어그램 + 주변 설명` |
| **4** | 공동 존 구조 + 현행 대비 | `좌우 2분할 비교` |
| **5** | 가드레일 17개 배치 | `전면 다이어그램` (요청→응답 흐름 위 오버레이) |
| **6** | 통합관리 4축 + 데이터 파이프라인 | `4분할` |
| **7** | 로드맵 3단계 | `3단계 가로 타임라인` |

### (b) 도해 지시

**1장 — 배치 진단 설계**
- 상단 : 3개 시나리오(S-A·S-B·S-C)를 가로 카드로. 각 카드에 부하 조건과 목적
- 하단 : 측정 5축을 **레이더 차트 축**으로 그리고, 「현행 측정 결과」와 「목표 수준」 두 개의 폐곡선을 겹쳐 표시. 두 곡선의 **간격이 큰 축이 곧 병목**임을 시각화 (실제 값은 진단 후 산출한다는 주석 병기)
- 레이더 차트 우측에 각 축의 측정 방법과 판정 기준을 표로

**2장 — 진단 축 3분할**
- 좌 `대고객 확대 수용성` / 중 `신기술 수용성` / 우 `정책변화 수용성`
- 각 열 : `판정 질문` → `근거 측정(축 번호 배지)` → `병목 유형 3개`
- **우측 열(정책변화)에 별도 강조** — 가상 정책 변경 3건 적용 실험을 아이콘으로 표현하고, *"애플리케이션마다 개별 수정이 필요하면 미흡"* 판정 기준을 굵게
- 하단 가로 띠 : 개선과제 우선순위 5기준을 **가중 순서대로 계단형**으로 배치. 최상단 「거버넌스 집행 가능성」에 강조

**3장 — 목표 아키텍처 5계층**
- 5계층을 세로로 적층(L1 데이터가 최하단, L5 관측이 최상단)
- 각 계층 좌측에 구성요소 블록들, **우측에 「유연성 확보 지점」을 별도 열**로 배치하고 다른 배경색. 이 오른쪽 열이 이 슬라이드의 차별 포인트이므로 시각적으로 분리
- L2 계층의 **게이트웨이 블록을 가장 크게** 그리고, 위아래 계층을 관통하는 **세로 관문선**을 그려 "모든 호출이 통과"를 표현
- L4 가드레일 계층에서 좌측으로 뻗어 나가는 화살표에 **「정책 저장소」 블록**을 배치하고, 그 블록에서 다시 과제1 산출물 아이콘(AI 업무규정·준칙·통제표)으로 연결. **정책이 규정에서 생성된다**는 경로가 보이게 한다
- 우측 여백에 계층 간 원칙 4개를 세로 목록으로

**4장 — 공동 존 구조**
- 좌우 2분할 : 왼쪽 「현행(진단 결과)」, 오른쪽 「목표」
- 오른쪽 패널에 3개 영역을 크기가 다른 블록으로 : **공동 존(공통비)** 을 가운데 크게, 좌우에 **은행 전용 / 상호금융 전용(직접비)**, 상단에 **가변 자원(변동비)**
- 각 블록에 **계측 태그 배지**를 붙이고, 블록 아래로 화살표를 내려 **「과제4 비용 구조」 상자**(공통비/변동비/직접비)에 1:1로 연결. 이 1:1 대응이 도해의 핵심
- 상호금융 전용 블록 안에 **조합 → 조합지점 2단 구조**를 작게 표시하여 계측 키가 1단 더 깊음을 명시

**5장 — 가드레일 배치도**
- 가로 흐름 : `사용자 → [요청 통제] → 게이트웨이 → 모델 → [응답 통제] → 사용자`
- 이 흐름 위에 R1~R6, P1~P5를 **통제 지점 마커**로 오버레이
- 흐름 좌측 상단에 별도 분기로 `개발 → [배포 통제 D1~D6] → 운영 환경` 을 그려 **배포 시점은 런타임과 다른 축**임을 표현
- 각 마커에 근거 점검항목 배지(⑤⑥⑦⑧⑫㉓㉕ 등)
- **D2 마커(고위험 의결번호 검증)** 와 **R5 마커(사용량 계측)** 를 가장 굵게 — 전자는 거버넌스 집행의 핵심, 후자는 정산의 원천
- 하단에 우회 경로 4개와 차단 방식을 표로, 차단 불가 시 SDK 적용 경로를 점선으로

**6장 — 통합관리 4분할 + 파이프라인**
- 상단 4분할 : `품질` / `사용량` / `비용` / `성과`. 각 칸에 메트릭 목록과 집계 단위 배지
- **「사용량」 칸에서 아래로 굵은 화살표**를 내려 하단의 **「과제4 정산」 상자**로 연결하고, 화살표 위에 계측 차원 6개를 나열. *"계측 단위 = 정산 변수"* 를 라벨로
- 하단 : L1~L10 파이프라인 가로 흐름 위에 9개 연결 지점을 **자동 전달 아이콘**으로 표시. **L6 → L7 연결(승인서 → 배포 조건)** 만 굵은 적색
- 파이프라인 아래에 *"재입력이 필요한 지점 = 증적 누락 지점"* 주석과 **재입력 지점 계수 표시란**

**7장 — 로드맵 3단계**
- 가로 타임라인 3구간(6개월 / 1년 / 2년), 구간 폭은 기간에 비례
- 각 구간 위에 주요 과제 4~5개를 칩으로, 구간 사이에 **판단 게이트 마름모**
- **각 마름모 안에 통과 요건을 수치로 표기**(게이트웨이 경유율 100% / 재입력 지점 0개 / 작업 단위 귀속)
- 타임라인 아래에 3개 띠 : `필요 역량` / `전제조건` / `구축사업 연계 조치`
- 좌측 끝에 **본 사업 종료 시점(D+150)** 마커를 찍어, 1단계가 본 사업과 겹치고 2·3단계는 이후임을 명시

### (c) 표·차트 사양

**표1. 배치 진단 측정 설계표** (1장 하단)

| 컬럼 | 측정 축 / 측정 지표 / 측정 방법 / 판정 기준 / 관련 진단 축 |
- 행 예시 1 : `③ 격리 | 서비스 간·기관 간 자원 간섭 정도 | 한 서비스에 부하를 몰아넣고 타 서비스의 지연 변화 측정 | 타 서비스 지연 증가가 허용 범위 이내인가, 은행·상호금융 간 간섭이 발생하는가 | 대고객 확대 수용성`
- 행 예시 2 : `⑤ 모델 교체 용이성 | 교체 작업 단계 수·소요시간, 애플리케이션 변경 필요 여부 | 서빙 중 모델을 다른 모델로 실제 교체 | 애플리케이션 코드 변경 없이 교체되는가 | 신기술 수용성`

**표2. 가드레일 명세표** (5장 또는 별지)

| 컬럼 | 번호 / 가드레일 / 집행 시점 / 집행 방식 / 근거 / 실패 시 동작 |
- 행 예시 1 : `D2 | 등급별 승인 검증 | 배포 | 등급에 따라 요구되는 결재 확인, 고위험은 AI윤리위원회 의결번호 필수 | 과제1 등급별 통제표 / AI RMF 3.4.2 | 배포 파이프라인 중단 및 요청자 통보`
- 행 예시 2 : `R3 | 중요정보 탐지·마스킹 | 요청 | 목적 외 고유식별정보·개인(신용)정보 탐지 후 마스킹 또는 차단 | 가이드라인 보안성 점검항목 ⑦ | 마스킹 후 진행 또는 차단 및 사유 기록`

**표3. 계측 차원 정의표** (6장)

| 컬럼 | 계측 차원 / 값 / 원천 / 수집 주기 / 과제4 용도 / 결측 시 대안 |
- 행 예시 1 : `부서/조합 | 은행: 본부 부서·영업점 / 상호금융: 조합 → 조합지점 | 게이트웨이 요청 태그 | 실시간 | 실비 정산의 배부 단위 | 인원수 배부키`

## 5. 인접 절과의 경계 / 인용 근거

### 경계 자기점검

- **Ⅲ.2.6과의 경계 — 이 절에서 가장 중요한 경계** : 기술 선택지(모델 게이트웨이 / SDK 내장 / 파이프라인 단계 삽입)의 **비교와 장단점 평가는 Ⅲ.2.6이 이미 확정**했다. 본 절은 그 결론(게이트웨이 주 + 파이프라인 필수 + SDK 선택 보완)을 **전제로 수용**하여 아키텍처를 설계했으며, **3방식을 재비교하지 않았다.** 반대로 Ⅲ.2.6은 아키텍처 다이어그램을 그리지 않았고, 본 절이 5계층 구조를 담당한다.
- **Ⅲ.4.2(과제1)와의 경계** : 위험등급 체계·필수통제 목록·데이터 등급·권한 매트릭스·CP 기록 항목은 Ⅲ.4.2가 확정했다. 본 절은 그것들을 **정책 저장소의 입력**으로 받아 집행 방식만 설계했다. 등급 임계값이나 통제 내용을 재정의하지 않았다.
- **Ⅲ.4.3(과제2)와의 경계** : 라이프사이클 10단계·게이트 판정 규칙·증적 12항목은 Ⅲ.4.3이 확정했다. 본 절은 그 **단계 명칭을 그대로 사용**하고(용어 변경 금지), 자동 전달 지점만 설계했다.
- **Ⅲ.4.5(과제4)와의 경계** : 본 절은 **계측 차원과 수집 방식**을 담당하고, **정산 산식·배분 비율·협의 절차는 Ⅲ.4.5**가 담당한다. 계측 차원의 값(기관·부서/조합·서비스·모델·자원 유형·비용 성격)은 두 절이 **동일하게 사용하는 공유 정의**이며, Ⅲ.4.5의 산식 초안이 본 절의 계측 요건에 선행 입력된다(Ⅲ.1.2 접합면 ③).
- **Ⅲ.4.1과의 경계** : Phase1의 플랫폼 진단은 **보안 통제 구현 여부와 계측 가능성 확인**에 한정된다. 본 절의 **실배치 확장성 진단은 Phase2**이며 목적과 시점이 다르다.
- **Ⅲ.1.2 Scope Out과의 관계** : **플랫폼 구축·개발 자체는 본 사업 범위 밖**이다. 본 절은 **기능 요건 명세 수준의 설계서**까지를 산출하며, 구현은 별도 구축사업이 수행한다. 로드맵의 투자 규모를 금액으로 특정하지 않은 것도 같은 이유다.

### [가정] 목록

- **[가정]** 현행 AI 플랫폼의 실제 구성(게이트웨이 존재 여부, 클라우드 구성, 서빙 방식, 계측 현황)은 확인되지 않았다. 본 절의 목표 아키텍처와 로드맵은 **배치 진단(4.4.1) 결과에 따라 조정**되며, 진단 전 확정 사항으로 제시하지 않는다.
- **[가정]** 배치 진단의 대상 과제 수(최소 2건, 권장 3건)와 대고객 트래픽 배수는 제안사 설계값이다. 실제 대상과 부하 조건은 착수 후 발주처와 확정한다.
- **[가정]** 처리량·지연의 판정 기준값(오류율 1% 이내, 허용 지연)은 서비스 성격에 따라 다르므로 본 절에서 특정하지 않았다. **기준값 설정 절차만 정의**했으며, 서비스별 기준값은 진단 착수 시 발주처와 합의한다.
- **[가정]** 공동 존의 논리 분리 방식(계정 / 네임스페이스 / 태그)은 현행 클라우드 구성에 따라 결정된다. 진단 후 확정하되, **분리 단위와 계측 태그의 일치**는 방식과 무관하게 유지한다.
- **[가정]** 로드맵 3단계의 기간(6개월 / 1년 / 2년)은 판단 게이트 통과를 전제로 한 계획값이다. 게이트 미통과 시 다음 단계로 진입하지 않으며, 기간은 실적에 따라 조정한다.
- **[가정]** 단계별 투자 금액은 제시하지 않았다. 구축 주체가 별도 사업이고 현행 구성·클라우드 계약 조건에 따라 편차가 크기 때문이며, **필요 역량과 과제 범위를 명세**하여 구축사업의 예산 산정을 지원한다. 산정 근거는 진단 결과를 반영해 DL3-2에 포함한다.
- **[가정]** 「AI 운영플랫폼 구축사업」의 설계 착수 시기와 확정된 기술 결정 사항은 확인되지 않았다. 착수 2주 내 확인하여 요건 선전달 시점과 제약조건을 확정한다(GM-01).
- **[가정]** AI-Agent의 도입 대상 업무와 시기는 결정되지 않았다. 3단계 과제로 배치하되, 실제 착수 여부는 2단계 게이트 통과 시점에 발주처가 판단한다. 다만 **세션·작업 단위 계측 스키마는 1단계에서 미리 포함**하여 이후 재구축을 방지한다.
