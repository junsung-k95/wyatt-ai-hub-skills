# Ⅲ.1.2 업무범위 및 추진과제 구조 (과제1~4)

> **메타** | 요구사항: `PD-III-1b` | Phase: 전기간 | 예상 분량: 2장

---

## 1. 거버닝 메시지

> **과제 1~4는 네 개의 별도 용역이 아니라 「규범 → 절차 → 시스템 → 정산」으로 이어지는 하나의 사슬이므로, 앞 과제의 산출물이 뒤 과제의 입력 규격이 되도록 설계하고 그 접합면을 계약 범위로 명시한다.**

- **서브메시지 1** — 과제1이 만든 위험등급·체크리스트는 과제3에서 **가드레일 코드로 시스템화**되고, 과제2가 정의한 라이프사이클 단계는 과제3의 **통합관리 기능 요건**이 되며, 과제3의 사용량 계측 단위는 과제4의 **정산 근거**가 된다. 접합면이 어긋나면 산출물은 각각 완성되어도 운영되지 않는다.
- **서브메시지 2** — 산출물 19종은 은행용·중앙회(상호금융)용으로 각각 작성·검수되므로 **실질 산출 단위는 19종이 아니라 최대 38벌**이다. 본 제안은 이원화 대상과 단일 작성 대상을 착수 시점에 확정하여 검수 부하를 관리한다.
- **서브메시지 3** — 책임한계를 Scope In / Scope Out으로 명시하되, Scope Out 항목마다 **"왜 제외인가 + 대신 무엇을 지원하는가"** 를 붙여 발주처가 후속 조치를 계획하도록 한다.

### 2.2 과제 간 의존관계 — 이 사업의 실제 구조

과제 간 연결은 "협조한다" 수준의 선언이 아니라 **산출물의 규격이 다음 과제의 입력 규격으로 고정되는 관계**다. 다음 다섯 개 접합면을 계약 범위로 명시한다.

#### 접합면 ① 과제1 → 과제3 : 위험평가체계·준칙이 가드레일로 시스템화된다

과제1은 AI서비스 위험평가체계를 만든다. 「금융분야 AI 위험관리 프레임워크(AI RMF)」 3.3.4가 제시하는 방식대로 **잔여위험 점수 합계가 25점 미만이면 저위험, 25점 이상 50점 미만이면 중위험, 50점 이상이면 고위험**으로 분류하고, 75점 이상이면 AI의사결정기구가 출시 여부를 재검토한다. 이 등급은 문서에만 남으면 실효성이 없으므로, 과제3에서 **플랫폼의 배포 게이트가 참조하는 값**으로 전달된다.

- **전달 규격** : 등급(저/중/고) + 필수통제 코드 목록 + 배포 승인권자 + 모니터링 주기 + 재평가 주기
- **과제3에서의 구현** : 고위험 등급 서비스는 AI윤리위원회 사전승인 의결번호가 입력되지 않으면 배포 파이프라인이 진행되지 않도록 차단
- **접합면이 어긋날 때의 결과** : 위험등급 체계가 3단인데 플랫폼 권한 모델이 2단이면, 중위험 서비스의 통제 수준을 시스템이 표현하지 못한다. 따라서 **등급 체계 확정(Phase1) → 플랫폼 권한 모델 설계(Phase2)** 의 순서를 고정한다.

#### 접합면 ② 과제2 → 과제3 : 라이프사이클 단계가 통합관리 기능 요건이 된다

과제2가 정의하는 라이프사이클 10단계(기획 → 타당성검토 → 데이터확보 → 개발/도입 → 평가검증 → 승인 → 배포 → 운영모니터링 → 재평가 → 폐기)는 과제3의 통합관리 화면에서 **서비스의 현재 상태 값**으로 사용된다.

- **전달 규격** : 단계 코드, 단계 진입·이탈 조건, 단계별 필수 증적 항목, 게이트 판정 결과(통과/조건부/반려)
- **접합면이 어긋날 때의 결과** : 매뉴얼의 단계 명칭과 플랫폼의 상태 값이 다르면 운영자가 두 개의 용어체계를 병용하게 되어 증적 추적이 끊긴다. **단계 명칭은 과제2가 확정하고 과제3은 그대로 사용한다**(용어 변경 금지).

#### 접합면 ③ 과제3 → 과제4 : 사용량 계측 단위가 정산 근거가 된다

과제4의 이용료 정산 산식은 **과제3이 계측하는 단위로만 구성한다.** 못 세는 것으로는 정산하지 못하기 때문이다.

- **전달 규격** : 계측 단위(호출 수 / 토큰 수 / GPU 시간 / 스토리지 GB·월 / 전용 인스턴스 시간), 집계 차원(기관 → 부서·지점 → 조합지점 → 서비스 → 모델), 집계 주기(일 단위 적재, 월 단위 마감)
- **역방향 제약** : 과제4가 필요로 하는 집계 차원이 과제3의 계측 설계에 없으면 산식을 실행하지 못하므로, **과제4의 산식 초안(Phase1)이 과제3의 계측 요건(Phase2)에 선행 입력**된다. 이는 Phase 순서와 역행하는 유일한 접합면이므로, Phase1 종료 시 「계측 요건 명세서」를 별도 전달문서로 남긴다.

#### 접합면 ④ 과제4 → Phase1 부속협약 : 배분 기준이 협약 별지가 된다

과제4가 산출하는 「AI서비스 비용 배분 기준안 및 협의서」(DL4-1)는 독립 문서로 끝나지 않고 **상호금융 업무위수탁 부속협약의 별지**로 편입된다(GM-07). 따라서 문서 형식을 협약 별지 규격(조·항·별표 체계, 서명란, 개정 절차 조항)으로 처음부터 작성한다.

#### 접합면 ⑤ 과제1 → 과제2 : 위험평가가 라이프사이클 게이트에서 호출된다

과제2의 게이트 중 「평가검증」·「승인」 단계는 과제1이 만든 위험평가 절차를 호출한다. 과제2는 **호출 시점과 필요 입력값만 정의**하고 평가 항목·배점은 정의하지 않는다(중복 방지).

### 2.3 책임한계 — Scope In / Scope Out

#### Scope In (본 사업 범위)

| 구분 | 포함 내용 |
|---|---|
| 규범 | AI 업무규정·운영준칙·분야별 준칙의 **조문 형태 제·개정안 작성**, 내부 승인 상신용 검토보고서 작성, 책무구조도 개정안(책무기술서 문안 포함) 작성 |
| 조직 | AI윤리위원회·AI실무협의회의 **구성안·운영준칙·1회차 안건 패키지** 작성 및 개최 지원 |
| 평가 | 위험평가 항목·배점·등급 산정식 설계, **10월 3개 과제에 대한 위험평가 실시 및 평가서 작성** |
| 절차 | 라이프사이클 정의서·단계별 업무매뉴얼 4종·게이트 체크리스트 작성, 성과지표 정의 및 산식 설계 |
| 당국 대응 | 혁신금융서비스 신청·변경·연장·개시신고 **서류 작성 및 제출 지원**, 금융보안원 실사자료 작성 및 **현장점검 배석 대응**, 금융감독원 클라우드컴퓨팅 이용보고 서류 작성 |
| 플랫폼 | 현행 플랫폼 진단(실배치 방식), 목표 아키텍처 **설계서**, 가드레일 기능 요건 정의, 로드맵 수립 |
| 비용 | 개발비·이용료 배분 산식 설계, 시산, 협의서·정산 가이드라인 작성, **중앙회 협의 회의 진행 및 쟁점 정리** |
| 교육 | 실제 케이스 기반 직원 교육 프로그램 설계 및 시행(SC2-18) |

#### Scope Out (본 사업 범위 외)

| 제외 항목 | 왜 제외인가 | 대신 무엇을 지원하는가 |
|---|---|---|
| **AI 플랫폼 시스템 구축·개발** | 본 사업은 컨설팅 용역이며, 구축은 별도 「AI 운영플랫폼 구축사업」의 범위다(GM-01이 그 연계를 전제한다) | 구축사업이 그대로 착수하도록 **기능 요건 명세 수준까지 설계서를 작성**하고, 구축사업 담당 조직과의 요건 인수인계 세션을 2회 이상 운영한다 |
| **AI 모델 개발·학습·튜닝** | 모델 성능 확보는 개별 서비스 개발 주체의 책임이며 본 사업의 위험평가 대상이지 수행 대상이 아니다 | 모델 위험요소 식별 기준과 **평가·검증 매뉴얼**을 제공하여 개발 주체가 자체 검증하도록 한다 |
| **내부 규정의 최종 제·개정 의결** | 이사회·위원회 의결은 발주처 고유 권한이다 | **상정 안건 패키지(개정 대비표·검토보고서·부의안)를 완성 형태로 제공**하고 상정 일정을 역산해 관리한다 |
| **중앙회와의 협약 체결 행위 자체** | 협약 당사자는 은행과 중앙회이며 제안사는 당사자가 아니다 | **협약 별지 문안·쟁점 정리표·대안 3안 비교표**를 제공하고 협의 회의를 진행·기록한다 |
| **금융보안원 보안성 검토의 결과 보증** | 심사 결과는 심사기관의 판단이다 | 실사자료를 **금융보안원 점검 관점으로 사전 자체점검**하고, 예상 질의 대응표를 작성하며, 현장점검에 배석하여 즉시 보완한다. 지적 발생 시 5영업일 내 보완자료 작성을 책임진다 |
| **기존 정보시스템의 운영·유지보수** | 본 사업 범위 밖의 상시 운영 업무다 | 해당사항 없음 |

### 2.4 산출물 이원화가 범위에 미치는 영향

RFP GM-15는 산출물을 **은행 및 중앙회(상호금융) 각각에 대해 작성하고 각각 검수**하도록 요구한다. 이를 그대로 적용하면 19종 × 2 = 38벌이 되어 Phase1 2개월 안에 검수를 마치지 못한다. 본 제안은 산출물을 세 유형으로 나누어 실질 산출 단위를 관리한다.

| 유형 | 정의 | 해당 산출물(예) | 실질 산출 벌수 |
|---|---|---|---|
| **단일 작성** | 양 기관에 동일하게 적용되며 기관별 차이가 없는 문서 | AI윤리원칙, 라이프사이클 표준 정의서, 플랫폼 목표 아키텍처 설계서 | 1벌 |
| **공통 골격 + 기관별 델타** | 본문은 공통, 기관 특성 부분만 분기 | AI 업무규정, 준칙 4종, 위험관리 업무매뉴얼, 정산 가이드라인 | 1벌 + 델타 2개 |
| **완전 분리** | 기관별로 내용이 전혀 다른 문서 | 책무구조도, 위험평가서, 거버넌스 승인서, 보안대책서 | 2벌 |

유형 판정은 착수 후 2주 내 발주처와 확정하며, 판정 결과는 Ⅲ.3.3 산출물 체계표의 「이원화 여부」 열에 반영한다. 제작·검수 병렬화 방법은 Ⅲ.2.3에서 다룬다.

### 2.5 수행 주체 구성

본 사업은 **주사업자 단독 수행**을 원칙으로 한다. 과제1~4 전 범위와 산출물 19종 전건에 대한 작성·검수 대응 책임을 주사업자가 단일하게 진다. 협력업체를 구성하지 않으므로 업무·범위·책임한계의 분할은 **해당사항 없음**이다(PD-I-2b). 다만 계약 협상 단계에서 발주처가 특정 영역(예: 클라우드 원가 산정 검증)에 외부 전문가 확인을 요구하면, 해당 검토 범위와 책임 한계를 별도 합의하여 반영한다.

## 3. 제안서용 요약 · 논리 구조

**논리 골격 : [구조 인식] → [의존관계] → [책임 경계] → [산출 부하 관리]**

- **[구조 인식]** 과제 4개 = 병렬 용역 ✗ / **「규범 → 절차 → 시스템 → 정산」 사슬** ○
  - 과제1 규범(9종) → 과제2 절차(6종) → 과제3 시스템(2종) → 과제4 정산(2종) = **19종**
- **[의존관계]** 접합면 5개를 **입력 규격으로 고정**
  - ① 과제1 위험등급(25/50/75점 기준) → 과제3 **배포 게이트 차단 조건**
  - ② 과제2 라이프사이클 10단계 → 과제3 **통합관리 상태값** (용어 변경 금지)
  - ③ 과제3 계측 단위 → 과제4 **정산 변수** (*못 세는 것으로는 정산 불가*)
  - ④ 과제4 배분 기준 → **업무위수탁 부속협약 별지**
  - ⑤ 과제1 위험평가 → 과제2 게이트에서 **호출만**
- **[책임 경계]** Scope In 8개 영역 / Scope Out 6개 항목 → **제외마다 대체 지원 명시**
  - 시스템 구축 ✗ → **요건 명세 수준 설계서 + 인수인계 2회**
  - 규정 의결 ✗ → **상정 안건 패키지 완성본 제공**
  - 협약 체결 ✗ → **별지 문안 + 쟁점표 + 대안 3안**
- **[산출 부하 관리]** 19종 × 2기관 = 38벌 ✗ → **3유형 분류**(단일 / 공통+델타 / 완전분리)로 실질 벌수 관리
- **[수행 주체]** 주사업자 단독 수행, 협력업체 해당사항 없음

## 4. 시각적 표현 방안

### (a) 슬라이드 분할 구조 — 2장

- **1장 : `중앙 다이어그램 + 주변 설명`** — 과제 의존관계 네트워크
- **2장 : `좌우 2분할 비교`** — Scope In ↔ Scope Out, 하단에 산출물 이원화 3유형 띠

### (b) 도해 지시

**1장 — 과제 의존관계 네트워크**
- 중앙 상단에 **과제1 노드(가장 크게)** 배치. 과제1이 다른 세 과제 모두에 입력을 공급하는 원천임을 크기로 표현
- 좌하단 과제2, 우하단 과제3, 최하단 과제4를 삼각 배치
- 화살표 5개를 **접합면 번호 배지(①~⑤)와 함께** 그린다. 각 화살표 위에 전달물 라벨을 짧게 표기
  - ① 과제1 → 과제3 : *"위험등급·필수통제 코드"*
  - ② 과제2 → 과제3 : *"단계 코드·게이트 판정"*
  - ③ 과제3 → 과제4 : *"계측 단위·집계 차원"*
  - ④ 과제4 → 협약 아이콘 : *"별지 편입"*
  - ⑤ 과제1 → 과제2 : *"위험평가 호출"*
- **③ 화살표만 역방향 점선 보조화살표(과제4 → 과제3, "계측 요건 선행 입력")를 추가**하고 적색으로 강조. Phase 순서와 역행하는 유일한 접합면이라는 점이 이 도해의 핵심 정보다
- 각 과제 노드 하단에 산출물 개수 배지(9 / 6 / 2 / 2)와 Phase 색상 띠
- 우측에 별도 세로 패널 : 접합면 5개를 **"어긋날 때의 결과"** 문장으로 한 줄씩 나열

**2장 — Scope In / Out 대비**
- 좌측(Scope In) : 8개 영역을 2열 × 4행 카드로. 카드마다 대표 산출물 번호 배지
- 우측(Scope Out) : 6개 항목을 세로 리스트로. **각 항목 아래에 들여쓴 「대신 지원」 문장을 반드시 병기**하고 다른 배경색으로 구분
- 중앙 경계선은 실선이 아닌 **점선 + "책임한계" 라벨**
- 하단 가로 띠 : 이원화 3유형(단일 / 공통+델타 / 완전분리)을 3분할로 배치, 각 칸에 해당 산출물 예시 2건씩

### (c) 표·차트 사양

**표1. 과제 범위 정의표** (1장 하단)

| 컬럼 | 내용 |
|---|---|
| 과제 | 과제1~4 |
| 범위 1줄 정의 | 제안사 언어 |
| 핵심 산출물 | DL 번호 및 종수 |
| Phase 배분 | Phase1 n종 / Phase2 n종 |
| 담당 요구사항 건수 | SC 건수 |

- 행 예시 1 : `과제1 | 누가 결정하고 누가 책임지며 무엇으로 통과시키는가 | DL1-1~1-9 (9종) | P1 5 / P2 4 | 23건`
- 행 예시 2 : `과제4 | 양측이 서명하는 개발비·이용료 산식 | DL4-1~4-2 (2종) | P1 2 | 4건`

**표2. Scope Out 및 대체 지원표** (2장 우측)

| 컬럼 | 내용 |
|---|---|
| 제외 항목 | — |
| 제외 사유 | 왜 본 사업 범위가 아닌가 |
| 대체 지원 내용 | 제안사가 대신 수행하는 것 |
| 후속 주체 | 구축사업 / 발주처 / 심사기관 등 |

- 행 예시 1 : `AI 플랫폼 시스템 구축 | 별도 구축사업 범위(GM-01) | 기능 요건 명세 수준 설계서 + 인수인계 세션 2회 | AI 운영플랫폼 구축사업`

## 5. 인접 절과의 경계 / 인용 근거

### 경계 자기점검

- **Ⅲ.1.1(사업목표)와의 경계** : 본 절은 목표를 재서술하지 않고 범위와 구조만 기술했다. 판정기준은 Ⅲ.1.1에 있다.
- **Ⅲ.1.3(Phase·우선순위)으로 넘긴 것** : Phase1 산출물 9건의 우선순위 정렬 논리. 본 절은 과제별 Phase 배분 개수만 표기했다.
- **Ⅲ.2.3(이원 산출물 전략)으로 넘긴 것** : 이원화 산출물의 제작·검수 병렬화 방법과 이견 조정 절차. 본 절은 **3유형 분류가 범위에 미치는 영향**만 기술했다.
- **Ⅲ.3.3(산출물 체계)으로 넘긴 것** : 산출물별 목차 수준 내역과 제출 시기(D+n).
- **Ⅲ.4.2~4.5로 넘긴 것** : 각 과제를 *어떻게* 수행하는지의 전부. 본 절은 접합면의 **전달 규격**만 명시했고 그 규격을 만드는 방법은 기술하지 않았다.
- **Ⅲ.4.6(산출물 목록·소유권)으로 넘긴 것** : 산출물의 권리 귀속과 양도 조건.

### [가정] 목록

- **[가정]** 「AI 운영플랫폼 구축사업」의 착수 시기·범위·발주 조직은 RFP에 명시되지 않았다. 본 절은 해당 사업이 본 사업과 병행 또는 후행한다는 전제로 인수인계 세션 2회를 계상하였으며, 착수 시 실제 일정을 확인하여 연계 계획을 확정한다(GM-01).
- **[가정]** 산출물 이원화 3유형의 배정(단일 / 공통+델타 / 완전분리)은 제안사의 유사 사업 경험에 근거한 초안이다. 최종 배정은 착수 후 2주 내 발주처 및 중앙회와 확정한다.
- **[가정]** 접합면 ③의 「계측 요건 명세서」는 RFP 산출물 목록에 없는 문서다. Phase1 종료 시 무상 제공하는 전달문서로 계상하였으며, 별도 공수를 요청하지 않는다.
- **[가정]** 상호금융 측 검수 주체가 중앙회 단일 창구인지 조합 단위 의견수렴을 포함하는지는 RFP에 명시되지 않았다. 단일 창구를 전제로 범위를 산정하였으며, 조합 단위 의견수렴이 필요하면 Ⅲ.2.3의 이견 조정 절차로 처리한다.
