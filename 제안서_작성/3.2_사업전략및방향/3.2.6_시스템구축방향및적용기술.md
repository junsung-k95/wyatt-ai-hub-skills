# Ⅲ.2.6 시스템 구축방향 및 적용기술

> **메타** | 요구사항: `PD-III-2b` | Phase: 전기간 | 예상 분량: 2장

---

## 1. 거버닝 메시지

> **문서로만 존재하는 거버넌스는 사람이 지킬 때만 작동하므로 규제기관 앞에서 증명되지 않으며, 규정·체크리스트·승인이 「요청 시점·응답 시점·배포 시점」 세 곳에서 시스템에 의해 강제 집행되는 방향으로 구축하되, 집행 지점의 기술 방식은 수협 현행 환경에 맞추어 모델 게이트웨이를 주(主)로 채택하고 나머지 두 방식을 보완적으로 결합한다.**

- **서브메시지 1** — 문서 기반 거버넌스와 시스템 기반 거버넌스의 차이는 "편의"가 아니라 **증적의 존재 여부**다. 「금융분야 AI 위험관리 프레임워크」 3.4.5는 위험평가·검증·통제 전 과정의 문서화를, AI기본법 시행령 제27조제2항은 조치 근거 문서의 **5년 보관**을 요구한다. 사람이 사후에 모으는 방식으로는 이 요구를 충족하지 못한다.
- **서브메시지 2** — 집행 방식은 **모델 게이트웨이 / SDK 내장 / 파이프라인 단계 삽입** 3가지다. 각각 언제 유효하고 무엇이 약한지를 비교한 뒤, 수협의 은행–상호금융 공동 존 구조에서는 **게이트웨이를 기본축으로 하고 배포 통제는 파이프라인, 내부 개발 서비스는 SDK로 보완**하는 조합을 권고한다.
- **서브메시지 3** — 설명가능성과 증적은 "필요할 때 만드는 자료"가 아니라 **라이프사이클 각 지점에서 자동 적재되는 로그**여야 한다. 무엇을·어디에·어떤 형식으로 남길지를 기술 방향의 일부로 지정한다.

## 2. 본문

### 2.1 왜 시스템화인가 — 문서 기반 거버넌스의 한계

| 구분 | 문서 기반 거버넌스 | 시스템 기반 거버넌스 |
|---|---|---|
| 통제 시점 | 사후(점검·감사 시) | **사전(요청·배포 차단)** |
| 준수 여부 | 담당자의 성실성에 의존 | 우회 불가(기술적 강제) |
| 증적 | 사후 수집, 누락 가능 | **발생 시점 자동 적재** |
| 규제 대응 | 자료 요구 시 재구성 | 조회로 즉시 제출 |
| 담당자 교체 | 판단 기준이 사람과 함께 이탈 | 기준이 코드·설정으로 잔존 |

**규제가 요구하는 수준** — 「금융분야 인공지능 가이드라인」 보안성 원칙 점검항목은 입출력 필터링 구현(⑤⑥), 목적 외 고유식별정보·개인신용정보 탐지 및 마스킹·차단(⑦), 모델 정보 노출 방지(⑧), 사용자별 질의 횟수 제한(⑫), 긴급정지 기능 구축(㉕)을 **"구현했는가"** 로 묻는다. 절차서 존재 여부가 아니라 **기능 구현 여부**를 묻는 문항이므로, 문서만으로는 YES로 답하지 못한다.

**따라서 본 사업의 시스템 구축방향은 다음 한 문장으로 정리된다.**

> *"과제1에서 만든 위험등급·필수통제·승인 절차를, 과제2가 정의한 라이프사이클 단계 위에서, 과제3의 플랫폼이 자동 집행하도록 한다."*

### 2.2 거버넌스 집행 지점 — 세 시점

거버넌스가 시스템에서 집행되는 지점을 세 시점으로 나눈다. 어떤 통제를 어느 시점에 걸 것인지가 설계의 출발점이다.

| 집행 시점 | 걸리는 통제 | 실패 시 결과 |
|---|---|---|
| **① 배포 시점** (Deploy-time) | 위험평가 완료 여부 / 등급별 승인권자 결재 / 고위험 시 AI윤리위원회 의결번호 / 승인 없는 모델 반입 차단 / 모델·데이터 형상 등록 | 평가받지 않은 서비스가 운영에 올라간다 |
| **② 요청 시점** (Request-time) | 입력 필터링(프롬프트 인젝션·탈옥 탐지) / 개인신용정보·고유식별정보 탐지 및 마스킹 / 사용자별 호출 한도 / 권한 검증 / 사용량 계측 기록 | 중요 정보가 모델로 흘러 들어간다 |
| **③ 응답 시점** (Response-time) | 출력 필터링(중요정보·모델정보 노출 차단) / 유해·부적절 응답 차단 / 생성형 AI 결과물 표시 / 이상 응답 탐지 / 응답 로그 적재 | 부적절한 결과가 고객에게 도달한다 |

세 시점 모두에서 **증적이 자동 적재**되며, 이것이 2.5의 설명가능성·증적 체계의 원천 데이터가 된다.

### 2.3 적용 기술 선택지 비교 — 3가지 방식

집행 지점을 구현하는 기술 방식은 세 가지다. 하나를 고르는 문제가 아니라 **어느 것을 기본축으로 하고 나머지를 어디에 보완할지**의 문제다.

| 평가축 | **A. 모델 게이트웨이 / 프록시** | **B. SDK 내장** | **C. 파이프라인 단계 삽입** |
|---|---|---|---|
| **방식** | 모든 AI 호출이 통과하는 중앙 프록시에서 정책 집행 | 각 애플리케이션이 통제 라이브러리를 탑재해 호출 전후 집행 | CI/CD·MLOps 파이프라인에 통제 단계를 삽입 |
| **언제 쓰는가** | 서비스가 다수이고 **모델·공급자가 자주 바뀔 때**, 여러 기관이 **같은 플랫폼을 공유**할 때 | 애플리케이션 수가 적고 **호출 맥락(사용자·업무)을 세밀히 알아야 하는 통제**가 필요할 때 | 통제 대상이 **배포·형상·산출물**일 때 |
| **집행 시점** | ② 요청 · ③ 응답 | ② 요청 · ③ 응답 (맥락 포함) | ① 배포 |
| **장점** | ① 애플리케이션 변경 없이 정책 일괄 적용 ② **호출 단위 계측이 한 곳에서 수집**되어 과제4 정산 근거로 직결 ③ 모델 교체 시 통제 재구현 불필요 ④ 기관·부서·조합 단위 태깅을 프록시에서 부여 | ① 업무 맥락(신청 고객·상품·직원 권한)을 반영한 정밀 통제 ② 프록시 미경유 경로도 커버 ③ 지연(latency) 추가 최소 | ① 승인 없는 모델·데이터의 운영 반입을 원천 차단 ② 형상·계보 정보가 배포 시점에 확정 ③ 기존 IT 배포 통제와 동일 체계로 운영 |
| **단점** | ① 프록시가 **단일 장애점**이 될 소지 ② 호출 지연 증가 ③ 프록시를 우회하는 직접 호출 경로가 있으면 통제 공백 | ① 애플리케이션마다 **적용·버전 관리 부담** ② 미적용 서비스는 통제 사각 ③ 정책 변경 시 재배포 필요 | ① 런타임 위험(프롬프트 인젝션, 정보 유출)에 무력 ② 파이프라인 밖 수동 배포 경로가 있으면 무력화 |
| **수협 현행 환경 적합도** | **높음** — 은행·상호금융이 **공동 존을 공유**하는 구조에서 기관별 태깅·계측·정책 분기를 한 지점에서 처리한다. 상용 생성형 AI 연계 이용 시 「AI 모델 연계」 구간의 암호·통제 요건 적용 지점과도 일치한다 | 중간 — 자체 개발 서비스에는 유효하나, 외부 SaaS형 AI 이용 시 적용 불가 | **높음** — 거버넌스 승인서(DL1-5) 발급 여부를 배포 조건으로 거는 데 가장 직접적 |

#### 권고안 : 게이트웨이 주(主) + 파이프라인 필수 + SDK 선택 보완

| 구성 | 역할 | 근거 |
|---|---|---|
| **모델 게이트웨이** (기본축) | 요청·응답 시점의 전 통제 + **사용량 계측의 단일 원천** | 공동 존 구조에서 기관·부서·조합 태깅을 한 지점에서 부여해야 과제4 정산이 성립한다. 모델·공급자 교체를 정책 재구현 없이 흡수한다 |
| **파이프라인 통제** (필수 병행) | 배포 시점의 게이트 승인 연동, 승인 없는 모델 반입 차단, 형상·계보 등록 | 런타임 통제만으로는 "평가받지 않은 서비스"를 막지 못한다. 게이트웨이와 성격이 겹치지 않는 통제이므로 선택이 아닌 병행 대상이다 |
| **SDK 내장** (선택 보완) | 업무 맥락 기반 정밀 통제가 필요한 **자체 개발 대고객 서비스**에 한정 적용 | 전면 적용은 관리 부담이 크므로, 고위험 등급 서비스에 한정한다 |

**권고 근거 요약** — 수협의 결정적 제약은 ① 은행·상호금융이 **같은 플랫폼을 공유**하고 ② 그 사용량이 **정산의 근거**가 되며 ③ 모델·공급자가 앞으로 바뀐다는 점이다. 세 제약 모두 **호출이 한 지점을 통과하는 구조**를 요구하므로 게이트웨이를 기본축으로 한다. 다만 게이트웨이는 배포 통제를 하지 못하므로 파이프라인을 병행한다.

**우회 경로 차단** — 게이트웨이 방식의 최대 약점은 우회 호출이다. 이에 대해 **네트워크 정책으로 모델 엔드포인트 직접 접근을 차단하고, 게이트웨이 경유만 허용**하는 것을 설계 전제로 명시한다. 이 전제가 성립하지 않는 구간이 발견되면 해당 구간에는 SDK 방식을 의무 적용한다.

### 2.4 클라우드 기반 및 공동 존 구조의 반영 (OBJ-08, OBJ-12)

본 사업의 데이터 거버넌스와 AI-Agent 확장은 클라우드 기반을 전제한다. 공동 존(Zone) 구조가 기술 방향에 부과하는 요건은 다음과 같다.

| 요건 | 내용 |
|---|---|
| **테넌시 구분** | 공동 존 안에서 은행·상호금융의 데이터·모델·로그를 **논리적으로 분리**하고, 분리 단위를 계측 태그와 일치시킨다. 분리 단위가 계측 단위와 다르면 정산이 성립하지 않는다 |
| **공통비·변동비 분리 계측** | 공동 존의 기본 인프라(항상 떠 있는 자원)와 사용량 비례 자원을 **별도 계정·태그로 분리**하여 수집한다(과제4의 공통비/변동비 구분과 정합) |
| **데이터 국외 이전 확인** | 클라우드 기반 AI서비스·상용 생성형 AI 이용 시 데이터의 국외 이전 가능성을 확인한다(가이드라인 보안성 점검항목 ㉖) |
| **보안 책임 분담 명확화** | 클라우드 제공업체와의 보안 책임 분담, 데이터 처리 지역, 암호화 수준, 접근 권한 관리에 대한 추가 통제를 적용한다(동 ㉝) |
| **모델 개선 목적 재사용 금지** | 외부 AI서비스 이용 시 입력 데이터가 모델 개선에 재사용되지 않도록 사전 확인하고 계약서에 명시한다(동 ㉗) |
| **연계 구간 보안** | 「외부망 연계」 구간과 「AI 모델 연계」 구간에 각각 요구되는 보안대책·암호알고리즘을 적용한다 |
| **AI-Agent 대비** | Agent는 **다단계 자율 호출**을 수행하므로, 게이트웨이가 개별 호출이 아니라 **세션·작업 단위로 계측·통제**하도록 설계한다. 계측 단위가 호출뿐이면 Agent 확장 시 정산과 통제가 모두 어긋난다 |

### 2.5 설명가능성 · 증적의 시스템 적재 방향 (SC2-21)

무엇을·어디에·어떤 형식으로 남길지를 기술 방향으로 지정한다. 상세 관리체계는 Ⅲ.4.3.6이 다룬다.

| 증적 항목 | 적재 시점 | 적재 위치 | 형식 |
|---|---|---|---|
| 모델 식별 정보(모델명·버전·공급자·체크섬) | 배포 시점 | 모델 레지스트리 | 구조화 레코드 |
| 학습데이터 출처·전처리 이력 | 데이터 파이프라인 실행 시 | 데이터 계보(Lineage) 저장소 | 계보 그래프 |
| 알고리즘 선택 근거·주요 변수 영향도 | 평가·검증 단계 | 기술문서 저장소 | 문서 + 메타데이터 |
| 위험평가 결과(항목별 점수·잔여위험·등급) | 평가 완료 시 | 거버넌스 저장소 | 구조화 레코드 |
| 게이트 판정 및 승인 이력(승인권자·의결번호·일시) | 각 게이트 통과 시 | 거버넌스 저장소 | 감사 로그 |
| 요청·응답 로그(입출력, 필터링 결과, 차단 사유) | 요청·응답 시점 | 운영 로그 저장소 | 구조화 로그 |
| 사용량 계측(기관·부서/조합·서비스·모델·토큰·시간) | 요청 시점 | 계측 저장소 | 시계열 |
| 모니터링 지표(성능·오류·민원 건수) | 운영 주기 | 관측 저장소 | 시계열 |

**보관 기간** — AI기본법 시행령 제27조제2항이 고영향 AI 관련 조치 근거 문서의 **5년 보관**을 요구하므로, 거버넌스 저장소의 위험평가·승인 이력은 **최소 5년** 보관을 기준으로 설계한다. 운영 로그·계측 데이터의 보관 기간은 정산 이의제기 기간과 감독당국 자료 요구 대응 기간을 고려하여 착수 후 확정한다.

**규제 대응 조회 요건** — 감독기관의 자료 요구에 대응하려면 **"서비스 단위로 한 번에 조회"** 되어야 한다. 따라서 위 8개 증적 항목은 저장소가 달라도 **서비스 ID를 공통 키로 연결**하는 것을 설계 요건으로 지정한다.

## 3. 제안서용 요약 · 논리 구조

**논리 골격 : [문제 인식] → [집행 지점] → [기술 선택지 비교] → [권고안] → [환경 제약] → [증적]**

- **[문제 인식]** 문서 기반 거버넌스 = **사후·사람 의존·증적 누락** / 시스템 기반 = **사전 차단·우회 불가·자동 적재**
  - 결정적 근거 : 가이드라인 보안성 점검항목이 *"구현했는가"* 를 묻는다(⑤⑥⑦⑧⑫㉕) → 문서로는 YES 불가
  - 한 문장 방향 : *"과제1의 위험등급·통제·승인을, 과제2의 라이프사이클 위에서, 과제3의 플랫폼이 자동 집행"*
- **[집행 지점]** 3시점 — **① 배포**(평가·승인·모델 반입 차단) / **② 요청**(입력 필터·정보 마스킹·한도·계측) / **③ 응답**(출력 필터·생성 표시·이상 탐지)
- **[기술 선택지]** 3방식 × 5평가축 비교
  - **A 게이트웨이** : 다서비스·모델 교체·공유 플랫폼에 유효 / 계측 단일 원천 ↔ 단일 장애점·우회 경로
  - **B SDK** : 업무 맥락 정밀 통제 ↔ 적용·버전 관리 부담, SaaS 적용 불가
  - **C 파이프라인** : 배포 원천 차단 ↔ 런타임 위험에 무력
- **[권고안]** **게이트웨이 主 + 파이프라인 필수 병행 + SDK 선택 보완(고위험 자체개발 한정)**
  - 근거 3제약 : ① 은행·상호금융 **플랫폼 공유** ② 사용량이 **정산 근거** ③ 모델·공급자 **교체 예정** → 모두 *"호출이 한 지점을 통과"* 를 요구
  - 약점 보정 : **네트워크 정책으로 모델 엔드포인트 직접 접근 차단**, 불가 구간은 SDK 의무 적용
- **[환경 제약]** 공동 존 7개 요건 — 테넌시 분리 = 계측 태그 일치 / 공통비·변동비 분리 계측 / 국외 이전 확인 / 책임 분담 / **재사용 금지 계약 명시** / 연계 구간 보안 / **Agent는 세션·작업 단위 계측**
- **[증적]** 8개 항목 × [적재 시점·위치·형식] 지정, **서비스 ID 공통 키 연결**, 거버넌스 저장소 **5년 보관**

## 4. 시각적 표현 방안

### (a) 슬라이드 분할 구조 — 2장

- **1장 : `좌우 2분할 비교`** — 왼쪽 「문서 기반 거버넌스」 ↔ 오른쪽 「시스템 기반 거버넌스」, 하단에 3개 집행 시점 띠
- **2장 : `전면 표`** — 기술 선택지 3열 × 5평가축 비교표. 하단에 권고 조합도와 증적 적재 지점 목록

### (b) 도해 지시

**1장 상단 — 문서 기반 ↔ 시스템 기반 대비**
- 좌우 패널 각각에 **동일한 5개 행**(통제 시점 / 준수 여부 / 증적 / 규제 대응 / 담당자 교체)을 배치하여 항목별 대비가 가로로 읽히게 한다
- 좌측 패널은 회색조 + 각 행에 **끊어진 사슬 아이콘**, 우측 패널은 강조색 + **잠긴 자물쇠 아이콘**
- 좌측 패널 위에 *"사람이 지킬 때만 작동"*, 우측 패널 위에 *"지키지 않으면 진행되지 않음"* 을 헤드라인으로
- 중앙 경계에 세로로 **가이드라인 점검항목 배지 6개**(⑤⑥⑦⑧⑫㉕)를 세워, 규제가 요구하는 것이 우측임을 표현. 이 배지 열이 이 슬라이드의 근거 장치다

**1장 하단 — 3개 집행 시점 띠**
- 가로 흐름 : `개발 → [① 배포 게이트] → 운영 → [② 요청] → 모델 → [③ 응답] → 사용자`
- 세 개의 집행 지점을 **마름모**로 표시하고, 각 마름모 아래에 걸리는 통제 목록을 3~5개 칩으로
- 각 마름모에서 아래로 **증적 적재 화살표**를 내려 하단의 저장소 아이콘 열로 연결
- 마름모 ①은 다른 두 개와 색을 달리하여 **배포 시점(사전) vs 런타임(실시간)** 의 성격 차이를 표시

**2장 상단 — 기술 선택지 비교표**
- 3열(A 게이트웨이 / B SDK / C 파이프라인) × 5행(방식·언제 쓰는가·집행 시점·장점·단점) + 「수협 적합도」 행
- 적합도 행은 **높음/중간** 을 색 블록으로 표기하고, A와 C에 강조 테두리
- 표 상단에 각 방식의 **소형 구조 아이콘**(프록시 관문 / 앱 내부 톱니 / 파이프라인 단계) 배치

**2장 하단 좌 — 권고 조합 구조도**
- 중앙에 **게이트웨이 블록(가장 크게)**, 좌측에 파이프라인 블록, 우측에 SDK 블록(가장 작게, 점선 테두리 = 선택 적용)
- 블록 크기 자체가 권고 비중을 표현
- 게이트웨이 블록 하단에서 뻗어 나오는 화살표에 **「계측 → 과제4 정산 근거」** 라벨을 굵게 — 게이트웨이 채택의 결정적 이유이므로
- 게이트웨이 좌측에 **차단선 아이콘 + "모델 엔드포인트 직접 접근 차단"** 주석

**2장 하단 우 — 증적 적재 지점 목록**
- 8개 항목을 2열 × 4행 소형 표로 배치, 각 항목에 적재 시점 배지
- 표 하단에 **「서비스 ID = 공통 키」** 를 가로 띠로 관통시켜 저장소가 달라도 연결됨을 표현
- 우측 끝에 **「5년 보관」** 배지(AI기본법 시행령 제27조제2항)

### (c) 표·차트 사양

**표1. 기술 선택지 비교표** (2장 주력)

| 컬럼 | 내용 |
|---|---|
| 평가축 | 방식 / 언제 쓰는가 / 집행 시점 / 장점 / 단점 / 수협 적합도 |
| A. 모델 게이트웨이 | 각 축의 값 |
| B. SDK 내장 | 각 축의 값 |
| C. 파이프라인 삽입 | 각 축의 값 |

- 행 예시 1 : `집행 시점 | ② 요청 · ③ 응답 | ② 요청 · ③ 응답(맥락 포함) | ① 배포`
- 행 예시 2 : `수협 적합도 | 높음 — 공동 존 공유 구조에서 기관 태깅·계측·정책 분기를 한 지점 처리 | 중간 — 자체 개발 한정, SaaS 적용 불가 | 높음 — 거버넌스 승인서 발급 여부를 배포 조건으로 직결`

**표2. 증적 적재 사양표** (2장 하단 또는 별지)

| 컬럼 | 내용 |
|---|---|
| 증적 항목 | 8종 |
| 적재 시점 | 배포 / 요청 / 응답 / 평가 / 운영 주기 |
| 적재 위치 | 저장소 명 |
| 형식 | 구조화 레코드 / 계보 그래프 / 감사 로그 / 시계열 / 문서+메타데이터 |
| 보관 기준 | 5년 / 착수 후 확정 |

- 행 예시 1 : `게이트 판정 및 승인 이력 | 각 게이트 통과 시 | 거버넌스 저장소 | 감사 로그 | 5년`
- 행 예시 2 : `사용량 계측(기관·부서/조합·서비스·모델·토큰·시간) | 요청 시점 | 계측 저장소 | 시계열 | 착수 후 확정(정산 이의제기 기간 고려)`

**차트1. 집행 시점별 통제 배치 매트릭스** (1장 보조 · 별지)
- 차트 종류 : 매트릭스 표(히트맵)
- 축 : 세로 = 통제 유형 10종(위험평가 확인·승인 검증·모델 반입 차단·입력 필터·정보 마스킹·호출 한도·출력 필터·생성 표시·이상 탐지·계측), 가로 = 집행 시점 3개(배포/요청/응답)
- 셀 값 : 해당 시점에 걸리는 통제를 ● 로 표시하고, 구현 방식(A/B/C)을 문자로 병기
- 목적 : 통제가 특정 시점에 몰리거나 비는 구간을 한눈에 확인

## 5. 인접 절과의 경계 / 인용 근거

### 경계 자기점검

- **Ⅲ.4.4(과제3)와의 경계 — 이 절에서 가장 중요한 경계** : 본 절은 **「방향과 기술 선택지」** 만 다루고, **목표 아키텍처 다이어그램은 그리지 않았다.** 5계층 아키텍처 설계, 계층별 구성요소, 가드레일의 상세 기능 정의, 통합관리 메트릭, 로드맵은 전부 Ⅲ.4.4가 담당한다. 본 절의 「권고 조합 구조도」는 아키텍처가 아니라 **기술 방식 선택의 결론**을 표현한 것이다.
- **Ⅲ.4.4가 본 절의 결론을 받는 방식** : Ⅲ.4.4는 게이트웨이 주(主) 권고를 **재비교하지 않고 전제로 수용**하여 아키텍처를 설계한다.
- **Ⅲ.4.2로 넘긴 것** : 위험등급 체계·필수통제 목록·승인권자 지정의 내용, 데이터 거버넌스의 관리기준·계보 방침. 본 절은 그것들이 **시스템에서 집행된다는 방향**만 기술했다.
- **Ⅲ.4.3.6으로 넘긴 것** : 증적 관리체계의 상세 — 증적 항목별 보관 기간 확정, 접근권한, 규제기관 요구 접수 시 산출까지의 대응 시한. 본 절은 **적재 시점·위치·형식의 기술 사양**만 지정했다.
- **Ⅲ.4.5로 넘긴 것** : 계측 값을 사용한 정산 산식. 본 절은 **계측이 게이트웨이에서 단일 원천으로 수집된다는 기술 방향**만 기술했다.
- **Ⅲ.2.4와의 경계** : 규제 추적은 Ⅲ.2.4가 담당한다. 본 절은 점검항목을 **기술 요건의 근거**로만 인용했다.

### [가정] 목록

- **[가정]** 수협의 현행 AI 플랫폼이 모델 게이트웨이 구조를 이미 갖추고 있는지, 또는 신규 도입이 필요한지는 확인되지 않았다. 본 절의 권고는 **방향 제시**이며, 현행 구조의 실제 확인은 Ⅲ.4.1 진단과 Ⅲ.4.4.1 배치 진단에서 수행한 뒤 Ⅲ.4.4.2 목표 아키텍처에 반영한다.
- **[가정]** 「모델 엔드포인트 직접 접근을 네트워크 정책으로 차단한다」는 설계 전제는 현행 네트워크 구성에 따라 실현 가능성이 달라진다. 진단 결과 차단이 불가한 구간이 확인되면 해당 구간에 SDK 방식을 의무 적용하는 것으로 대체한다.
- **[가정]** 공동 존의 테넌시 분리 방식(계정 분리 / 태그 기반 / 네임스페이스 분리)은 현행 클라우드 구성에 따라 결정된다. 착수 후 확인하여 계측 태그 체계와 일치시킨다.
- **[가정]** 운영 로그·계측 데이터의 보관 기간은 정산 이의제기 기간과 감독당국 자료 요구 대응 기간을 고려해야 하므로, 착수 후 발주처 정보보호·준법감시 부서와 확정한다. 본 절은 거버넌스 저장소의 5년 보관만 법정 요건으로 확정했다.
- **[가정]** AI-Agent의 세션·작업 단위 계측은 향후 Agent 도입을 전제로 한 설계 요건이다. 현 시점의 Agent 도입 계획과 범위는 Ⅲ.4.4.5 로드맵 수립 시 발주처와 확정한다.
